# Mini NPU Simulator

MAC(Multiply-Accumulate) 연산으로 입력 패턴이 어느 필터에 더 가까운지 판정하는 Python 콘솔 프로그램입니다.

## 실행 방법

```bash
python main.py                 # 프로그램 실행
python -m doctest -v main.py   # 단위 테스트 (정규화·MAC·판정 등 24개)
```

- 환경: Python 3.8 이상. 외부 라이브러리 없이 표준 라이브러리(`json`, `time`, `math`, `os`, `re`, `sys`, `gc`, `statistics`, `platform`, `datetime`, `unicodedata`)만 사용합니다. Python 3.8.20과 3.13.18에서 실행을 확인했습니다.
- data.json 위치: `main.py`와 **같은 폴더**에 둡니다. 다른 폴더에서 실행해도 `main.py` 옆의 data.json을 읽습니다.
- 모드 2를 실행하면 같은 폴더에 실패 사유 로그 `mini_npu.log`가 만들어집니다. (실행할 때마다 새로 씀)

실행하면 입력 방식을 고릅니다. `1` 또는 `2`를 입력하고, 그 외 값을 넣으면 다시 묻습니다.

```

[모드 선택]
1. 사용자 입력 (3x3)
2. data.json 분석
선택:
```

## 구현 요약

### 데이터 구조
`Matrix` 클래스가 n×n 값을 2차원 리스트로 저장합니다. `set(row, col, value)`로 특정 위치에 저장하고 `get(row, col)`로 읽습니다. 크기 제한이 없어 3×3, 5×5, 13×13, 25×25를 모두 처리합니다.

### 라벨 정규화
data.json은 같은 대상을 위치마다 다른 표기로 씁니다. 그대로 비교하면 `'+'`와 `'cross'`가 서로 다른 문자열이 됩니다. 그래서 읽는 즉시 프로그램 내부 표준 라벨 `Cross`, `X`로 바꿉니다.

| 위치 | 입력 | 표준 라벨 |
|---|---|---|
| expected 값 | `'+'` | `Cross` |
| expected 값 | `'x'` | `X` |
| filter 키 | `'cross'` | `Cross` |
| filter 키 | `'x'` | `X` |

이 표에 없는 값은 해당 케이스(또는 필터)를 FAIL 처리하고 사유를 출력합니다. 콘솔 출력과 PASS/FAIL 비교는 표준 라벨로만 합니다.

**정규화 전용 함수 `normalize_label(raw, kind)`.** 모든 라벨 변환은 이 함수 하나로 합니다. `kind`는 `"expected"` 또는 `"filter"`이고, 규칙에 없는 표기는 `None`을 돌려줍니다. 함수로 분리한 이유는 다음과 같습니다.
- **모듈화:** 라벨 규칙(매핑 표)과 판정 로직이 분리되어, 규칙이 바뀌어도 판정·출력 코드는 그대로 둡니다.
- **재사용:** expected 값과 filter 키처럼 서로 다른 곳에서 같은 함수로 변환해, 변환 방식이 어긋날 일이 없습니다.
- **테스트 용이성:** 입력과 출력이 분명한 작은 함수라서 단위 테스트를 붙이기 쉽습니다.

**정규화 단위 테스트 케이스** (`python -m doctest -v main.py`로 실행, `normalize_label`의 docstring에 포함)

| 호출 | 기대 결과 |
|---|---|
| `normalize_label("+", "expected")` | `'Cross'` |
| `normalize_label("x", "expected")` | `'X'` |
| `normalize_label("cross", "filter")` | `'Cross'` |
| `normalize_label("x", "filter")` | `'X'` |
| `normalize_label("X", "expected")` | `None` (규칙에 없는 표기) |
| `normalize_label("cross", "expected")` | `None` (filter 키 표기는 expected로 인정하지 않음) |
| `normalize_label(None, "expected")` | `None` (문자열이 아님) |

doctest에는 이 밖에 `Matrix` 저장·읽기, 행/열 검증, MAC(명세 Case 1 = 5, Case 2 = 1), 동점 판정, 측정값 요약, 모드 1 입력 검증 테스트도 들어 있습니다. 실행 결과는 `24 passed`입니다.

### 새 라벨 추가 절차
라벨 목록은 `STANDARD_LABELS` 한 곳에서 관리합니다. 판정(`decide`), 점수 출력, 필터 필수 검사, 성능 측정이 모두 이 목록을 따르므로, 아래 순서대로 하면 판정·출력 코드는 고치지 않아도 됩니다. (예: 원 모양 `Circle` 추가)

1. **표준 라벨 추가:** `main.py`에 `LABEL_CIRCLE = "Circle"`을 만들고 `STANDARD_LABELS = (LABEL_CROSS, LABEL_X, LABEL_CIRCLE)`로 바꿉니다.
2. **정규화 맵 추가:** `EXPECTED_TO_LABEL`에 `"o": LABEL_CIRCLE`, `FILTER_KEY_TO_LABEL`에 `"circle": LABEL_CIRCLE`을 추가합니다.
3. **단위 테스트 추가:** `normalize_label`의 docstring에 `normalize_label("o", "expected")` → `'Circle'`, `normalize_label("circle", "filter")` → `'Circle'` 예시를 넣고 `python -m doctest -v main.py`로 통과를 확인합니다.
4. **필터 데이터 추가:** data.json의 **모든** `size_N` 항목에 `"circle"` 필터(N×N)를 추가합니다. 표준 라벨의 필터가 하나라도 없으면 그 크기는 로드 실패로 처리되기 때문입니다.
5. **패턴 샘플 추가:** `patterns`에 `"expected": "o"`인 케이스를 넣습니다. (예: `size_5_3`)
6. **실행 확인:** 모드 2를 실행해 필터 로드 줄에 `(Cross, X, Circle)`이 나오는지, 케이스마다 `Circle 점수` 줄이 나오는지, 새 케이스가 `판정: Circle | expected: Circle | PASS`인지 확인합니다.

위 절차를 복사본에 그대로 적용해 확인했습니다. 원·십자가·X 패턴 3개가 모두 PASS였고, 원 패턴의 점수는 Cross 4.0, X 0.0, Circle 12.0이었습니다.

### MAC 연산
MAC(Multiply-Accumulate)은 두 배열의 같은 위치 값을 곱하고(Multiply), 그 결과를 모두 더하는(Accumulate) 연산입니다. 결과 점수가 클수록 패턴이 그 필터와 비슷합니다. (명세 예시: 십자가 입력 × 십자가 필터 = 5, 십자가 입력 × X 필터 = 1)
AI 모델은 큰 필터를 많이 사용하므로 이미지 한 장에도 MAC 연산이 아주 많이 필요합니다. 그래서 MAC 속도가 AI 처리 속도를 좌우하고, MAC을 대량으로 동시에 처리하는 NPU가 쓰입니다.

이 프로그램은 NumPy 없이 2중 반복문으로 MAC을 구현했고, 점수(float)를 반환합니다.

```python
total = 0.0
for i in range(n):              # 행 우선(row-major) 순서로 접근
    for j in range(n):
        total += pattern.get(i, j) * filt.get(i, j)
return total
```

**연산 횟수 예시.** 칸마다 곱셈 1번과 덧셈(누적) 1번을 합니다.

| 크기 | 곱셈 | 덧셈 | 패턴 1개 판정 (필터 2개) |
|---|---|---|---|
| 3×3 | 9번 | 9번 | 곱셈 18번 + 덧셈 18번 |
| 5×5 | 25번 | 25번 | 곱셈 50번 + 덧셈 50번 |
| 13×13 | 169번 | 169번 | 곱셈 338번 + 덧셈 338번 |
| 25×25 | 625번 | 625번 | 곱셈 1,250번 + 덧셈 1,250번 |

### CPU와 NPU
- **CPU:** 고성능 코어 몇 개가 복잡한 명령과 분기를 순서대로 빠르게 처리합니다. 범용성은 높지만, 같은 MAC을 수백만 번 반복하는 일은 코어 수만큼만 동시에 할 수 있습니다.
- **NPU:** 단순한 MAC 연산기 수천 개를 배열로 묶어 한 번에 처리합니다. MAC처럼 규칙적인 연산에서는 처리량과 전력 효율이 높습니다. 반면 지원하는 연산과 정밀도가 정해져 있어, 범용 작업이나 분기가 많은 작업에는 맞지 않습니다.
- **실제 병목은 데이터 이동(메모리 대역폭)입니다.** MAC 1번에는 값 2개(입력, 가중치)를 메모리에서 가져와야 합니다. 연산기가 아무리 많아도 메모리가 값을 공급하는 속도보다 빨리 계산할 수는 없습니다.
  - 이 프로그램의 25×25 MAC도 625번 곱할 때마다 값 2개를 새로 읽고 다시 쓰지 않으므로, 계산보다 읽기가 많은 구조입니다.
  - 실제 이미지 처리에서는 같은 필터를 이미지의 여러 위치에 반복해서 씁니다. 그래서 NPU는 필터 가중치를 칩 안의 메모리에 올려 두고 재사용해 메모리 접근을 줄입니다.
  - 1000×1000에서는 이 프로그램의 행렬 3개가 약 96MB로, CPU의 L2 캐시(이 측정 환경 4MB)보다 훨씬 커서 같은 문제가 더 두드러집니다. (아래 "대형 입력" 참고)

### 동점 처리 정책 (epsilon)
`abs(score_a - score_b) < 1e-9`이면 동점으로 봅니다. 그 외에는 점수가 큰 쪽으로 판정합니다. 동점이면 점수 차이와 기준값을 함께 출력합니다. (예: `|Cross-X| = 1.11e-16 < 1e-9`)
모드 2에서는 판정(Cross/X)이 expected와 같으면 PASS, 다르면 FAIL입니다. UNDECIDED는 expected와 같을 수 없으므로 FAIL입니다.

**모드 1과 모드 2의 표기가 다른 이유.** 두 모드는 같은 판정 함수 `decide`와 같은 epsilon 규칙을 씁니다. 다른 것은 라벨 이름뿐입니다. 모드 1의 필터는 사용자가 직접 입력한 것이라 Cross/X라는 의미가 없으므로, 명세의 모드 1 출력 정의(A / B / 판정 불가)를 따릅니다. 모드 2는 expected와 비교해야 하므로 표준 라벨(Cross / X / UNDECIDED)을 씁니다.

**1e-9를 쓰는 이유 (스케일 근거).**
- data.json의 점수는 0.1 ~ 52.9 범위입니다. 판정이 실제로 갈리는 케이스의 점수 차이는 최소 8.8입니다.
- 부동소수점(double) 누적 오차는 이 데이터에서 최대 2.66e-15입니다. (double의 상대 정밀도 약 1.1e-16 × 수십 번의 덧셈)
- 1e-9는 이 오차보다 약 10⁵~10⁶배 크고, 실제 차이(8.8)보다 약 10⁹배 작습니다. 그래서 오차는 동점으로 흡수하고, 실제 차이는 정상적으로 판정합니다.

**대체 값 범위.** 이 data.json에서 같은 결과(동점 3건)가 나오는 epsilon을 계산하면 `2.66e-15 < epsilon ≤ 8.8`입니다. 점수가 0~수십 정도인 이 과제에서는 1e-12 ~ 1e-6 사이 값이 모두 1e-9와 같은 결과를 냅니다.
- 1e-15로 줄이면: size_5_1만 동점이 되고, 나머지 2건은 오차 방향으로 판정됩니다.
- 10으로 늘리면: 실제 차이가 8.8인 size_5_2까지 동점이 됩니다.

**절대 기준의 한계와 대안.** 오차는 덧셈 횟수와 점수 크기에 비례해 커집니다. 1000×1000 무작위 데이터로 실측하면 점수가 약 250,046일 때 누적 오차가 5.2e-9로, 1e-9보다 컸습니다. 큰 입력에서는 `math.isclose(a, b, rel_tol=1e-9, abs_tol=1e-9)`처럼 점수 크기에 비례하는 상대 허용오차를 함께 써야 합니다. (같은 실측의 상대 오차는 2.1e-14) 이 과제는 명세 권장 기준인 절대값 1e-9를 사용합니다.

**참고.** 같은 수식도 더하는 방식에 따라 오차가 달라집니다. Python 3.12부터 내장 `sum()`은 보정 합산을 써서 0.1을 9번 더하면 정확히 0.9가 됩니다. 반면 차례로 누적하면 0.8999999999999999입니다. 이 프로그램은 MAC을 반복문으로 직접 누적하므로 Python 3.8과 3.13에서 점수가 똑같습니다.

### 2. FAIL 원인 분석

실패 3건(size_5_1, size_13_2, size_25_1)의 원인을 "데이터/스키마 문제 → 로직 문제 → 수치 비교 문제" 순서로 확인했습니다.

**데이터/스키마 문제: 해당 없음.** 3건 모두 키에서 N이 정상 추출되었고, 패턴과 필터의 크기가 같습니다. expected(`'x'`, `'+'`)와 필터 키(`'cross'`, `'x'`)도 표준 라벨로 정규화되었습니다. 같은 크기의 다른 케이스(size_5_2, size_13_1, size_25_2)는 PASS입니다.

**로직 문제: 해당 없음.** data.json의 값으로 직접 계산한 결과와 프로그램 점수가 일치합니다. 3건 모두 수학적으로는 두 점수가 같습니다.

| 케이스 (입력 모양) | Cross 필터와 겹치는 칸 | X 필터와 겹치는 칸 |
|---|---|---|
| size_5_1 (X) | 가운데 1칸: 0.9 × 1 = 0.9 | 대각선 9칸: 0.1 × 9 = 0.9 |
| size_13_2 (십자가) | 십자 25칸: 0.3 × 25 = 7.5 | 가운데 1칸: 7.5 × 1 = 7.5 |
| size_25_1 (X) | 가운데 1칸: 4.9 × 1 = 4.9 | 대각선 49칸: 0.1 × 49 = 4.9 |

**수치 비교 문제: 원인.** 0.1과 0.3은 2진 부동소수점으로 정확히 표현되지 않습니다. 그래서 여러 번 더하면 아주 작은 오차가 생깁니다. (0.1을 차례로 9번 더하면 0.9가 아니라 0.8999999999999999)
3건의 점수 차이는 각각 1.11e-16, 2.66e-15, 1.78e-15로 모두 1e-9보다 작습니다. 따라서 동점 정책에 따라 UNDECIDED가 되고, expected(X, Cross, X)와 다르므로 FAIL입니다. 명세의 결과 예시에서도 0.9 대 0.8999999999999999는 `UNDECIDED | FAIL (동점 규칙)`로 처리됩니다.

**epsilon 정책이 필요한 이유.** epsilon 없이 `>`로만 비교하면 3건은 각각 Cross, X, Cross로 판정됩니다. 이 판정은 패턴 모양이 아니라 1e-16~1e-15 수준의 반올림 오차로 정해진 것입니다. epsilon 정책을 쓰면 이런 차이를 동점으로 처리해, 오차로 판정이 갈리지 않게 합니다.

**참고: 점수 정규화.** MAC 점수는 필터 가중치의 크기에 비례합니다. data.json의 필터 가중치 합은 크기마다 크게 다릅니다.
- size_5: Cross 8.9 / X 0.9
- size_13: Cross 7.5 / X 14.7
- size_25: Cross 52.9 / X 4.9

점수를 각 필터의 가중치 합으로 나누면(또는 코사인 유사도를 쓰면) "필터 모양을 얼마나 채웠는지"로 비교하게 됩니다. 이렇게 계산하면 3건은 모두 expected와 같아집니다.
- size_5_1: Cross 0.1011 / X 1.0000 → X
- size_13_2: Cross 1.0000 / X 0.5102 → Cross
- size_25_1: Cross 0.0926 / X 1.0000 → X

명세가 점수를 "위치별 곱의 합"으로 정의하므로 프로그램의 판정에는 적용하지 않았습니다.

### 3. 성능 분석과 시간 복잡도 O(N²)

측정 환경: Intel Xeon 2.10GHz, 논리 코어 2개, 메모리 약 7GB / Linux / Python 3.13.18. 측정값은 MAC 1회 평균이고, 필터별 10회 측정했습니다. 수치는 실행할 때마다, 컴퓨터마다 달라질 수 있습니다.

| 크기(N×N) | 평균 시간(ms) | 연산 횟수(N²) | 최소(ms) | 최대(ms) | 표준편차(ms) |
|---|---|---|---|---|---|
| 3×3 | 0.0011 | 9 | 0.0010 | 0.0020 | 0.0003 |
| 5×5 | 0.0023 | 25 | 0.0022 | 0.0026 | 0.0001 |
| 13×13 | 0.0138 | 169 | 0.0127 | 0.0283 | 0.0034 |
| 25×25 | 0.0483 | 625 | 0.0453 | 0.0639 | 0.0040 |

**연산 횟수.** MAC은 N×N개 칸마다 곱셈 1번과 덧셈 1번을 합니다. 따라서 연산 횟수는 N²이고, 시간 복잡도는 O(N²)입니다.

**측정 결과와의 연결.**
- 5×5 → 13×13: 연산 횟수는 169 / 25 ≈ 6.8배, 평균 시간은 0.0138 / 0.0023 ≈ 6.0배입니다.
- 13×13 → 25×25: N은 약 1.9배, 연산 횟수는 625 / 169 ≈ 3.7배, 평균 시간은 0.0483 / 0.0138 ≈ 3.5배입니다.
- 25×25 → 1000×1000 (아래 대형 입력 실측): 연산 횟수는 1,600배, 평균 시간은 약 85ms / 0.0483ms ≈ 1,760배입니다.
- 시간 증가율이 N의 증가율이 아니라 N²의 증가율을 따릅니다.
- 평균보다 크게 나오는 회차도 있지만(13×13 최대 0.0283ms), 표준편차는 평균의 약 4~27% 수준이라 크기별 추세를 비교하기에 충분합니다.

**상수 요인과 실제 측정값의 차이.** O(N²)는 늘어나는 추세만 나타냅니다. 실제 시간은 `T(N) ≈ a·N² + b`입니다.
- `a`는 원소 1개를 처리하는 시간으로, 이 환경에서 약 77~87ns입니다. CPU, Python 버전, `get()` 호출 같은 구현 방식에 따라 달라지는 상수 요인입니다. (같은 코드도 Python 3.8에서는 원소당 약 185~200ns)
- `b`는 함수 호출처럼 크기와 무관한 고정 시간입니다.

그래서 작은 크기에서는 `b`의 비중이 커서 시간 비율이 N² 비율보다 조금 낮게 나옵니다. 크기가 클수록 `a·N²`가 대부분을 차지합니다.

### 4. 대형 입력(1000×1000) 처리

프로그램은 크기 제한이 없어, data.json에 `size_1000` 필터와 패턴을 넣으면 그대로 처리합니다. 1000×1000 행렬을 JSON에서 읽어 직접 측정한 결과는 다음과 같습니다. (위와 같은 환경)

| 항목 | 실측값 |
|---|---|
| MAC 1회 시간 | 약 83~87ms (원소당 83~87ns) |
| 성능 표 방식(필터 2개 × 10회) 측정 시간 | 약 1.7초 |
| 행렬 1개 메모리 (2차원 리스트) | 32.1MB (원소당 32바이트: 리스트 칸 8바이트 + float 객체 24바이트) |
| 케이스 1건 (패턴 + Cross + X 필터) | 약 96MB |
| JSON 텍스트 크기 (행렬 1개, 소수 3자리) | 6.9MB, 읽는 동안 최대 메모리 40.9MB |
| 같은 값을 `array('d')` 1차원 배열로 저장 시 | 8.2MB (약 1/4) |
| 누적 부동소수점 오차 (무작위 값) | 5.2e-9 (1e-9보다 큼) |

**문제점**
- **시간:** 25×25보다 연산이 1,600배 많습니다. 케이스나 필터가 많아지면 그 배수만큼 늘어납니다. (예: 패턴 100개 × 필터 2개 ≈ 17초)
- **메모리:** Python 리스트는 숫자마다 별도 객체를 만들어 원소당 32바이트를 씁니다. 실제 값(8바이트)의 4배입니다. json 모듈은 파일 전체를 한 번에 읽어 피크 메모리가 더 큽니다.
- **캐시:** 행렬 3개(약 96MB)는 이 환경의 L2 캐시(4MB)보다 훨씬 크고, 일반 PC의 L3 캐시(대개 수~수십 MB)보다도 큽니다. 그래서 계산보다 메모리에서 값을 가져오는 시간이 늘어납니다. 측정 방식에 따라 원소당 83~123ns로, 작은 크기(약 75ns)보다 같거나 느리게 나왔는데, 이 차이가 그 영향으로 보입니다. (추정)
- **정확도:** 누적 오차가 1e-9를 넘으므로, 절대 기준 epsilon만으로는 동점 판정이 흔들릴 수 있습니다. (위 "동점 처리 정책" 참고)

**최적화 우선순위** (이 프로그램 기준, 효과가 큰 순서)
1. **1차원 연속 배열로 저장:** 2차원 리스트 대신 길이 N²의 `array('d')`를 쓰면 메모리가 약 1/4(32MB → 8MB)로 줄고, 값이 메모리에 연속으로 놓여 캐시 효율이 좋아집니다. `data[i][j]`의 2단계 접근도 `data[i*N + j]` 한 번으로 줄어듭니다.
2. **행 단위(스트리밍) 처리:** MAC은 한 번 훑으면 끝나는 연산이므로, 행을 하나씩 읽으면서 누적하면 메모리가 O(N²)에서 O(N)으로 줄어듭니다. 단, JSON은 통째로 읽어야 하므로 행 단위로 읽을 수 있는 형식(예: 한 줄에 한 행)이 필요합니다.
3. **병렬화:** 케이스·필터별 MAC은 서로 독립이라 나눠서 동시에 계산할 수 있습니다. 1000×1000 한 개도 행 블록으로 나눠 부분합을 더하면 됩니다. Python에서는 GIL 때문에 스레드로는 빨라지지 않으므로 `multiprocessing`(프로세스)을 써야 합니다. 프로세스 생성과 데이터 전달 비용이 있어서, 작은 크기에서는 오히려 느리고 큰 입력에서만 효과가 있습니다.
4. **블록화와 접근 순서(stride):** 현재 반복문은 행 우선으로 접근해, 행 우선으로 저장된 데이터를 순서대로(stride 1) 읽습니다. 열 우선으로 돌면 한 번에 N칸씩 건너뛰며 읽어(stride N) 캐시 효율이 크게 떨어집니다. 하나의 패턴을 여러 필터와 비교하거나 이미지 위에서 필터를 옮겨 가며 계산할 때는, 블록 하나를 캐시에 올린 채로 여러 번 재사용하는 블록화가 효과적입니다. 순수 Python에서는 객체 처리 비용이 더 커서 우선순위가 낮지만, C나 NPU에서는 1번과 함께 가장 중요한 최적화입니다.
5. **수치 정책:** 큰 입력에서는 상대 허용오차(`math.isclose`)를 쓰고, 정확도가 중요하면 `math.fsum`처럼 오차를 보정하는 합산을 검토합니다.
